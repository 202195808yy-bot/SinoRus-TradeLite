# TradeHub — платформа совместной работы для трансграничной торговли России и Китая

**Язык:** [Русский](README.md) · [English](README.en.md)

Курсовой проект по дисциплине **«Разработка веб-приложений на Python»**.

Веб-приложение на Django, реализующее клиентскую часть платформы: сведение
разрозненных сведений и задач нескольких сторон сделки (продавец, покупатель,
перевозчик, брокер) на одну временную шкалу.

## Мобильный клиент

Параллельно с веб-версией по дисциплине **«Технологии разработки мобильных
приложений»** разрабатывается мобильный клиент той же платформы
(React Native). Первый этап этой дисциплины — описание предметной области и
перечень функциональных требований — выполнен; документ на двух языках
приложен в `docs/`.

Мобильный клиент не дублирует веб-версию, а обслуживает действия «на месте»:
подтверждение, отметку этапов, съёмку документов, сканирование кодов и работу
без сети. Соответствие модулей мобильного приложения модулям веб-версии:

| FM1 | Аутентификация и профиль | 4 | M1 |
| FM2 | Главный экран и задачи | 4 | M8 |
| FM3 | Запросы и предложения | 4 | M3 |
| FM4 | Заказы и исполнение | 5 | M4 |
| FM5 | Документы и сканирование | 5 | M6 |
| FM6 | Логистика и отслеживание | 4 | M5 |

Из 48 требований 25 имеют высокий приоритет, 19 — средний и 4 — низкий.
Дополнительно установлены 12 нефункциональных требований. Модуль FM10 не
имеет соответствия в веб-версии: работа без сети и очередь отложенных
операций — свойство именно мобильного клиента.

Тот же документ доступен в формате markdown на трёх языках:
`docs/mobile/mobileapp.ru.md`, `docs/mobile/mobileapp.zh.md` и
`docs/mobile/mobileapp.en.md`. Markdown-версии и файлы `.docx` собираются из
одного источника данных, поэтому таблицы и числа в них совпадают.

## Быстрый старт

```bash
# 1. Установить зависимости
pip install -r requirements.txt

# 2. Применить миграции
python manage.py migrate

# 3. Запустить сервер разработки
python manage.py runserver
```

Приложение доступно по адресу <http://127.0.0.1:8000/>,
административная панель — <http://127.0.0.1:8000/admin/>.

### Требования к окружению

Ветка Django 4.2 официально поддерживает Python 3.8–3.12. Проект тем не
менее запускается и на более новых версиях — вплоть до 3.14: несовместимость
в копировании контекста шаблона обходится на месте, без правки
`site-packages` и без изменения `requirements.txt` (см. `core/compat.py`).

| Python | Django | Состояние |
|---|---|---|
| 3.8–3.12 | 4.2.30 | штатный режим, обход не включается |
| 3.13 | 4.2.30 | штатный режим, обход не включается |
| 3.14 | 4.2.30 | работает через `core/compat.py` |

Обход включается в `CoreConfig.ready()` и только тогда, когда родная
реализация действительно сломана: проверка не по номеру версии, а по факту —
копируется пустой контекст. Если копирование проходит, вмешательства нет,
и поведение Django остаётся нетронутым.

## Структура приложений

Проект разделён по ограниченным контекстам предметной области: помимо ядра
`core` он включает десять доменных приложений. Ядро не содержит моделей
предметной области — в нём собраны общие механизмы (реестр страниц, реестр
данных, словари интерфейса, переключение языка, настройка панели).

| Приложение | Назначение | Модули | Моделей |
|---|---|---|---|
| `core` | ядро: общие механизмы, реестры, переводы | — | 0 |
| `accounts` | организации и пользователи | M1 | 5 |
| `catalog` | товарная номенклатура и справочники | M2 | 8 |
| `trading` | запросы, предложения, заказы | M3–M4 | 9 |
| `logistics` | партии, перевозки, инциденты | M5 | 7 |
| `documents` | документооборот и соответствие | M6 | 6 |
| `messaging` | двуязычная переписка | M7 | 4 |
| `tasks` | задачи и напоминания | M8 | 4 |
| `analytics` | показатели, риски, панель | M9 | 3 |
| `billing` | счета, платежи, сверка | M10 | 4 |
| `system` | аудит и параметры системы | M11 | 2 |

Каждое доменное приложение автономно: объявляет собственные модели,
представления, маршруты с отдельным пространством имён и реестр данных
(`<app>/datasets.py`), а связь с ядром ограничена импортом общих
конструкторов блоков. Зависимости между приложениями однонаправлены:
`catalog` и `accounts` — нижний слой, `trading` зависит от них,
`logistics` — от `trading`, `documents` — от `catalog`, `logistics` и
`trading`, `analytics` — от `trading`, `billing` — от `catalog` и
`trading`; циклов нет.

**Разделение не потребовало переноса данных.** Имена таблиц в базе
оставлены прежними: каждая модель явно закрепляет `db_table = "portal_<имя>"`,
поэтому физические таблицы, имена индексов и содержимое базы не изменились.
Маршруты тоже сохранены — изменились только пространства имён
(`portal:` → `<приложение>:`), адреса страниц остались прежними.

## Единый реестр страниц

Ключевое архитектурное решение — модуль `core/pages.py`. Он содержит
единственный источник данных обо всех страницах приложения и используется
тремя потребителями:

* `<app>/urls.py` — построение маршрутов (своё пространство имён);
* `core/views.py` и `<app>/views.py` — представления;
* `docs/pages.{ru,zh,en}.md` и документ «Описание страниц приложения» —
  описание страниц.

Благодаря этому перечень страниц в коде, в репозитории и в пояснительной
записке не может разойтись.

Каждая запись реестра хранит название, назначение и содержание страницы на
трёх языках (русский, китайский, английский); описания параметров маршрута
заданы словарём по языкам. Значения читаются через хелперы `title_of()`,
`purpose_of()`, `content_of()`, `params_of()` и `module_name()`, поэтому
добавление четвёртого языка не требует правок у потребителей.

Документ этапа 2 — `docs/Описание_страниц_приложения.docx` (ПЗ, 32 с.,
43 страницы, 12 модулей) и его китайская версия
`docs/Описание_страниц_приложения_CN.docx` (27 с.). Таблицы страниц
строятся непосредственно по реестру, поэтому перечень в документе и в
коде согласован по построению.

## Модели приложения

Этап 3 реализует модели данных в доменных приложениях (`<app>/models.py`): 52 модели Django
покрывают 56 сущностей предметной области (9 классов). Четыре сущности
реализованы не таблицами, а полями и словарями значений: характеристики
товара — JSON-полем `Good.attributes`, роль — словарём `Membership.Role`,
файл (медиа) — полями `FileField` и моделью `Attachment`, термин
глоссария — статическим справочником интерфейса.

| Что | Сколько | Где |
|---|---|---|
| Модели | 52 | `<app>/models.py` |
| Поля (без PK) | 394 | то же |
| Ограничения целостности | 23 | `Meta.constraints` моделей |
| Индексы прикладного уровня | 11 | `Meta.indexes` моделей |
| Вычисляемые свойства | 9 | свойства моделей |
| Автонумеруемые документы | 7 | `DocNumberMixin` |

Общие механизмы: абстрактная модель `TimeStampedModel` с отметками
времени, `DocNumberMixin` для номеров вида `RFQ-2026-0001` (важно
порядок базовых классов — `class Rfq(DocNumberMixin, TimeStampedModel)`),
десятичные суммы `DecimalField`, словари `TextChoices`, русскоязычные
`verbose_name` у каждого поля.

```bash
python manage.py migrate           # создать 53 таблицы
python manage.py seed_demo         # демонстрационная цепочка сделки
python manage.py test core.tests   # 141 тест: модели, страницы, языки, совместимость
```

Команда `seed_demo` идемпотентна (повторный запуск не создаёт дублей) и

маршрута → инцидент → комплект документов → сертификат с истекающим
сроком → диалог с переводом → задача → счёт, платёж и сверка.

## Шаблоны страниц приложения

Этап 4 подключает страницы к моделям. Единый реестр данных
`core/datasets.py` (конструкторы блоков и сводный реестр) и реестры `<app>/datasets.py` ставят в соответствие каждой странице функцию-провайдер
контекста `provider(request, **kw)`, возвращающую набор блоков
(`kpi` — показатели, `table` — таблица с ячейками-ссылками и метками,
`fields` — карточка полей, `list` — краткий список). Универсальный шаблон
`templates/portal/_blocks.html` отображает эти блоки, поэтому одна и та же
разметка обслуживает и главную страницу, и списки, и карточки.

| Что | Сколько | Где |
|---|---|---|
| Страниц с данными из моделей | 37 | `<app>/datasets.py` |
| Страниц-прототипов (без данных) | 6 | `about`, `help`, `login`, `register`, `logout`, `admin_index` |
| Всего страниц | 43 | `core/pages.py` |

Провайдеры работают с реальными запросами ORM: списки используют
`select_related`/`prefetch_related` и ограничение выдачи (`LIST_LIMIT = 50`
с признаком усечения), карточки — `get_object_or_404`, списки предложений —
агрегат `Max("versions__version")` для номера последней версии. Суммы
выводятся в русском формате (пробел как разделитель тысяч, запятая в
дробной части). Если пользователь не аутентифицирован, корпоративные
страницы показывают данные первого предприятия и помечаются режимом
`demo` (разграничение прав — этап 5).

Документ этапа — `docs/Представления_и_данные.docx` (ПЗ, 26 с.) и его
китайская версия `docs/Представления_и_данные_CN.docx` (26 с.). Таблицы
соответствия строятся программно: провайдер каждой страницы вызывается на
демонстрационных данных, а фактические таблицы БД определяются перехватом
SQL-запросов, поэтому документ не расходится с кодом.

```bash
python tools/check_data.py     # 37 страниц с данными, 6 прототипов
python manage.py test core.tests  # 141 тест: модели, страницы, языки, совместимость
```

## Пользователи приложения

Этап 5 проектирует подсистему пользователей. Документ этапа —
`docs/Пользователи_приложения.docx` (ПЗ, 33 с.) и его китайская версия
`docs/Пользователи_приложения_CN.docx` (29 с.).

Замысел опирается на признак `access` в реестре `core/pages.py`, который
существует с этапа — и до сих пор нигде не проверялся.

| Что | Значение |
|---|---|
| Уровни доступа страниц | `public` (5 страниц), `auth` (34), `role` (4) |
| Роли участников | 6 (`Membership.Role`) |
| Матрицы прав | «роль × модуль», «роль × действие» |
| Предлагаемые разрешения уровня модели | 13 на 11 моделях |
| Место проверки доступа | общий построитель страниц `core/views.py` |

Решения этапа:

* роль хранится в `Membership` (связь «пользователь — предприятие —
  роль»), поэтому один человек может работать в нескольких предприятиях
  с разными ролями;
* проверка доступа выполняется централизованно, а не декораторами в 43
  представлениях: `public` — всем, `auth` — вошедшим, `role` — только
  администратору предприятия (иначе 403, а для анонимного посетителя —
  302 на `accounts:login` с параметром `next`);
* значимые операции защищаются пользовательскими разрешениями
  (`Meta.permissions`), выдаваемыми группам по ролям;
* демонстрационный режим этапа 4 отключается — иначе проверку доступа
  можно обойти запросом без сессии.

Проектные решения зафиксированы в документе; их реализация в коде —
следующий шаг.

## Язык интерфейса

Интерфейс переключается между русским, китайским и английским языками.
Переключатель `RU · 中文 · EN` расположен в правой части шапки.

Механизм собственный, без `gettext`: источником переводов служат данные
проекта, а не файлы `.po`/`.mo`. Поэтому нет второго набора переводов,
который мог бы разойтись с кодом.

| Слой | Источник перевода | Объём |
|---|---|---|
| Названия страниц, назначение, содержание, параметры маршрута | реестр `core/pages.py` (поля `ru`/`zh`/`en`) | 43 страницы |
| Названия модулей M0..M11 | реестр `core/pages.py` | 12 модулей |
| Тексты оболочки: навигация, кнопки, заголовки разделов, подвал | `core/i18n.py`, словарь `UI` | 51 ключ |
| Подписи блоков данных: заголовки таблиц и колонок, подписи KPI, ключи полей, пустые состояния | `core/labels.py`, словарь `LABELS` | 385 строк |
| Перечисления моделей: статусы, виды документов, единицы измерения, роли, категории, «да»/«нет» | `core/labels.py` (сверяется с `choices` моделей) | 108 из 117 |
| Значения справочников: страны, валюты, единицы измерения, типы документов, отрасли, категории товаров | `core/labels.py` (сверяется с `name_zh` справочника) | 12 |
| Подписи административной панели: названия приложений, моделей и полей, `help_text`, подписи `choices`, заголовки панели | `core/admin_labels.py` (сверяется с метаданными ORM) | 297 |
| Подписи, которые панель берёт из базы: разрешения (`Permission.name`) и сообщения журнала (`LogEntry.change_message`) | `core/admin_i18n.py` — собираются заново из `codename` и из перевода названий полей | 2 механизма |
| Подписи внутри `__str__` моделей («Профиль: …», «пошлина», «НДС», «Диалог: …», «Перевод #…») | `core/labels.py`, через `i18n.label()` | 3 новых слова |
| Подписи автосозданных моделей связи M2M («Связь dialog-user»), видны на странице подтверждения удаления | `core/admin_labels.py`, через `admin_i18n.tr_through_label()` | 2 слова × 4 модели |

Выбор языка выполняет `core.middleware.LanguageMiddleware`: параметр
`?lang=` запоминается в сессии, поэтому дальнейшие переходы по ссылкам
сохраняют язык.

**Что переводится, а что нет.** Граница проходит не по признаку «подпись
или ячейка», а по признаку «есть ли строка в словаре»:

* переводятся подписи, **перечисления** (`choices` моделей) и **значения
  справочников** — они интерфейс, хотя и приходят значениями ячеек;
* **не переводятся свободные данные**: наименования предприятий и
  товаров, номера документов, адреса, даты, суммы, свободные примечания.
  Их в словаре нет, поэтому `i18n.tr_value()` возвращает их как есть —
  подменять данные словарём значило бы искажать содержимое.

Раньше правило было грубее («ячейки не переводим»), и вместе с данными
мимо словаря проходили русские статусы и виды документов. Дополнительно
распознаются два составных случая: «Заказ #1» (подпись плюс номер) и
значения, склеенные разделителем («Недовоз · Повреждение», «RU — Россия»).

```bash
/?lang=zh              # китайский интерфейс
/orders/?lang=en       # английский на странице списка заказов
```

Тот же выбор действует и в административной панели `/admin/`:
переключатель `RU · 中文 · EN` стоит в её шапке (на странице входа — рядом
с заголовком), а штатные надписи Django (кнопки, пагинация, темы) панель
берёт из своих переводов. Ссылки переключателя ведут на отдельный маршрут:

```bash
/lang/zh/?next=%2Fadmin%2F   # китайская панель, возврат на /admin/
```

Отдельный маршрут нужен потому, что параметр `?lang=` в списках панели
Django считает неизвестным фильтром и отвечает лишним перенаправлением
(`/admin/trading/order/?lang=zh` → `302` на `?e=1`). Маршрут
`core:set_language` хранит адрес возврата в `next`, принимает только
собственные пути (защита от открытого перенаправления) и совместим с
параметром `?lang=` в адресах приложения. Выход из системы тоже сохраняет
выбранный язык: `auth_logout()` очищает сессию целиком, поэтому
представление выхода восстанавливает выбор.

**Подписи панели приходят из метаданных ORM**, а не из провайдеров
страниц: названия моделей и полей панель читает у самих моделей
(`verbose_name`, `help_text`, подписи `choices`). Штатные переводы Django
их не покрывают, поэтому оболочка панели оставалась русской, даже когда
выбран китайский язык. Метки обёрнуты в ленивый перевод
(`core/admin_i18n.py`) — строка переводится в момент вывода, когда
язык уже известен:

| Обёртка | Что оборачивает | Почему так |
|---|---|---|
| `LazyRu` | `verbose_name`, `help_text`, заголовки панели | не подкласс `str`: `django.utils.text.capfirst()` проверяет `isinstance(x, str)` и подкласс вернул бы русский текст как есть |
| `LazyChoice` | подписи `choices` | подкласс `str`, потому что `<app>/datasets.py` их склеивает, а миграции записывают; переводится только `str()` |

Обёртки применяет `CoreConfig.ready()` обходом моделей, поэтому новые
модели и поля переводятся автоматически. Миграции при этом не меняются:
`makemigrations` сравнивает `Options.original_attrs`, а не обёрнутые
значения. Подписи ищутся сначала в `ADMIN_LABELS`, затем — без учёта
регистра — в `LABELS`: у моделей подписи со строчной буквы («валюта»), у
страниц с прописной («Валюта»), и общий словарь даёт им один перевод.
Осознанные расхождения (`создан` → «创建人», а на страницах «Создан» это
состояние «已创建») перечислены в `admin_labels.OVERRIDES` явно.

Свободные данные панель по-прежнему показывает как есть — в том числе
ключи JSON-полей: панель это форма редактирования, и переведённый ключ
при сохранении записался бы в базу вместо исходного. Названия языков в
переключателе (`title="Русский"`) — тоже намеренно: каждый язык подписан
сам собой.

**Две подписи панель хранит не в метаданных, а в базе**, и они тоже
заморожены по-русски:

* `Permission.name` — при `migrate` в него записывается «Can add
  <verbose_name_raw>», то есть русское название модели навсегда (Django
  берёт непереведённое имя намеренно, чтобы данные не зависели от локали).
  В панели это список разрешений на странице пользователя и группы:
  «Can add вложение». Подпись собирается заново из `codename` — глагол
  берётся из штатного каталога Django (то же слово, что у ссылок панели:
  Добавить / 增加 / Add), название модели — из её `verbose_name`.
* `LogEntry.change_message` — JSON с названиями изменённых полей,
  записанными в момент правки. Django переводит сообщение целиком, но
  русских названий полей в каталоге нет, поэтому в китайской панели
  выходило «已修改статус 和 дата подписания». Названия подменяются до
  форматирования, а сама запись в базе не меняется.

Наконец, подписи внутри `__str__` моделей («Профиль: …», «пошлина»,
«НДС», «Диалог: …», «Перевод #…») записаны жёстко, но панель показывает
объект в списках, хлебных крошках и выпадающих списках — то есть вне
`translate_blocks`. Поэтому такие слова берутся из словаря через
`i18n.label()`; подпись `Profile` совпадает с названием модели
(«Пользователь» / «用户»), как эта сущность названа и в документах этапа 1.

**Отдельный случай — автосозданные модели связи M2M** (`Dialog.participants`,
`User.groups` и другие). Их подпись Django собирает из переводимой строки
«%(from)s-%(to)s relationship» и подставляет имена модели и поля сразу,
при импорте `models.py`, когда активна локаль по умолчанию, — получается
обычная русская строка «Связь dialog-user», которую ленивый перевод уже
не берёт. Вдобавок у такой модели нет своего `__str__`, поэтому панель
показывала служебное «Dialog_participants object (1)». То и другое видно
на странице подтверждения удаления, где Django перечисляет связанные
объекты. Поэтому `get_models()` (он не возвращает автосозданные модели,
`include_auto_created` по умолчанию выключен) обходится отдельно:
переводится только первое слово подписи, а «dialog-user» остаётся —
это техническое имя, одинаковое на всех языках; и задаётся читаемый
`__str__` вида «Диалог: ORD-2026-0001 — ivanov».

Названия страниц и подписи блоков берутся из того же источника, что и
документы этапов 1–4, поэтому интерфейс и ПЗ не расходятся. Полнота
словаря проверяется автоматически: провайдеры вызываются на
демонстрационных данных, а перечисления, значения справочников и подписи
панели собираются обходом метаданных моделей — каждая такая строка
обязана иметь перевод.

```bash
python tools/check_lang.py   # 385 подписей + 108 перечислений + 12 справочников + 286 подписей панели + 8 подписей связей M2M
```

Китайская версия описаний страниц не содержит кириллицы (кроме
общепринятого обозначения ИНН), русская — иероглифов; это проверяется
тестами. Исторические ключи `purpose`/`content` в реестре страниц
(синонимы китайских вариантов) больше не используются шаблоном напрямую —
представление подставляет перевод текущего языка, поэтому русский
заголовок больше не сопровождается китайским текстом.

Страницы панели проверяются так же — целиком, по отрисованному HTML,
включая списки, формы, историю и страницы пользователя с группами.
Кириллица допускается только в свободных данных (их слова собираются из
базы по всем приложениям, включая обрезки длинного текста), в названиях
языков у переключателя (`title="Русский"`) и не считается вовсе в
комментариях разметки и стилей: пользователь их не видит.

## Прокрутка боковой панели

Боковая панель TradeHub и панель разделов в админке — самостоятельные
прокручиваемые области (`overflow: auto`), а браузер сохраняет прокрутку
только у окна. Поэтому после любого перехода панель откатывалась к первому
пункту, и нужный модуль приходилось искать заново.

`static/js/keep-scroll.js` запоминает положение в `sessionStorage`
(на вкладку — так же, как Django хранит фильтр в панели админки) и
возвращает его после загрузки. Панель TradeHub помечена атрибутом
`data-keep-scroll="sidebar"`; панель админки создаётся Django и атрибута не
имеет, поэтому скрипт находит её по `id="nav-sidebar"`.

**В узком окне панель ведёт себя иначе**, и это второй, менее очевидный
случай. Ниже `@media (max-width: 900px)` у `.sidebar` снимаются
`position: sticky` и `max-height`: панель перестаёт прокручиваться сама и
тянется на полторы тысячи пикселей перед содержимым, прокручивается вся
страница. Сохранять `scrollTop` панели там бессмысленно — он всегда ноль,
— поэтому скрипт сохраняет и возвращает прокрутку **страницы**. Какой из
двух случаев, видно на месте: панель прокручивается сама, только если
содержимое выше неё. Возврат прокрутки страницы происходит лишь тогда,
когда уходили, видя навигацию: переход из содержимого читателя к панели не
возвращает.

Возврат повторяется после полной загрузки, если разметка ещё не была
разложена, и на время возврата отключается плавная прокрутка, чтобы это не
превращалось в анимацию при каждом переходе. Если `sessionStorage` недоступен
(приватный режим), страница работает как раньше.

> **Ловушка при проверке.** Весь код оформлен как немедленно вызываемая
> функция, и это необходимость, а не стиль: `return` вне функции
> недопустим в обычном скрипте, и файл с ним целиком не выполняется в
> браузере. `node --check` такой ошибки не показывает — он оборачивает
> файл в функцию. Проверять разбор нужно `new vm.Script(...)`; именно так
> делает `tools/keep_scroll_harness.js`.

## Совместимость с Python 3.14

`requirements.txt` закрепляет Django 4.2.30 — ветку, которая поддерживает
Python 3.8–3.12 (3.13 появилась в Django 5.1, 3.14 — в 5.2). Но проект
запускают и на более новых версиях: виртуальное окружение `.venv` собрано
на Python 3.14.

Тогда ломается копирование контекста шаблона. Django 4.2 делает так
(`django/template/context.py`):

```python
def __copy__(self):
    duplicate = copy(super())
    duplicate.dicts = self.dicts[:]
    return duplicate
```

Приём опирается на то, что у объекта `super()` чтение атрибута
делегируется обёрнутому экземпляру, поэтому `copy(super())` возвращает
копию **контекста**, а не самого `super`. В Python 3.14 это поведение
изменилось, и вторая строка падает:

```
AttributeError: 'super' object has no attribute 'dicts'
and no __dict__ for setting new attributes
```

Внешне это выглядит обманчиво: главная страница панели открывается (она
контекст не копирует), а **любой переход** — на список моделей, на карточку,
на пользователя — отвечает ошибкой 500. В наборе тестов падали 40 из 120 —
все, что отрисовывают шаблон с копированием контекста.

Обход — `core/compat.py`:

1. **проверка по факту, а не по номеру версии** — копируется пустой
   контекст; если копия создалась, вмешательства нет;
2. **подмена только при поломке** — `BaseContext.__copy__` заменяется
   реализацией без `super()`, повторяющей исходную семантику (новый объект,
   тот же `__dict__`, отдельный список `dicts`);
3. **идемпотентность** — признак `_core_compat` не даёт подменить дважды;
4. включается в `CoreConfig.ready()`, рядом с переводом подписей панели.

`site-packages` не правится, зависимостей не добавлено,
`requirements.txt` по-прежнему закрепляет `Django==4.2.30`. На Python 3.12
и 3.13 обход не включается вовсе — поведение Django остаётся штатным.
Проверяется в `core/tests/test_compat.py`.

## Границы предметной области

Платформа занимает позицию «слой торговой кооперации» и намеренно не выполняет:

1. платёжные операции — только фиксация состояния платежа и подтверждение сторонами;
2. таможенное оформление и сертификацию — только сбор, проверка и напоминания;
3. вынесение итогового суждения о соответствии — только факты и перечень недостающих документов;
4. сбор персональных данных, не связанных с деловой необходимостью.
